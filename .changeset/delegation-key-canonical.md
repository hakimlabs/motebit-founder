Delegation-family keys verify only in their canonical spelling (64 lowercase hex, the pattern the committed `standing-delegation-v1` / `delegation-token-v1` / `delegation-revocation-v1` JSON Schemas already declare). `findGrantRevocation` binds a revocation to a grant by exact `delegator_public_key` equality, but the verifiers decoded keys leniently (`"AB"` ≡ `"ab"`, `"0g"` ≡ `"00"`), so a revocation the delegator signed with another spelling of its key verified yet bound nothing, and a grant spelled in uppercase verified yet could not be revoked by the delegator's canonical revocation — `verifyDelegationTokenVerdict` reported `revocation: fresh` and `isFullyVerified: true`, and the runtime's `verifyGrantForTurn` returned a verified grant, for a revoked grant. Now `verifyDelegation` and `verifyStandingDelegation` reject a non-canonical delegator or delegate key, `verifyDelegationRevocation` rejects a non-canonical delegator key, and `signDelegation`, `signStandingDelegation` and `signDelegationRevocation` throw on one rather than emit an artifact every verifier rejects (spec §5: a producer MUST NOT emit a non-canonical key).

Stricter verification: a delegation artifact whose key is uppercase, mixed-case or non-hex no longer verifies. Fresh mints and the CLI emit lowercase (`bytesToHex`), and the wire schemas already refuse other spellings, so no artifact a schema accepts is affected. A stored identity config could carry another spelling of the same key; the molecule-runner self-grant mint now canonicalizes it (see the ignored changeset). The relay's comparison of a revocation's key against the keys it holds for the delegator stays case-insensitive (legacy device rows); only the artifact's own key must be canonical.

`motebit` (CLI): `motebit grant revoke` on a stored grant whose delegator key is not canonical prints one line saying the grant verifies nowhere and is already inert, and exits 1 — before the passphrase prompt — instead of dying on the signer's throw.
